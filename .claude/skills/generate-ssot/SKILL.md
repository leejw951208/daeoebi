# Generating SSOT Docs

## Overview

코드베이스를 심층 분석해 **SSOT(Single Source of Truth) 문서 세트**를 `docs/ssot/`에 생성한다. 목적은 "문서와 코드가 어긋나지 않는 단일 진실 원천"을 만드는 것이다. 그래서 이 스킬의 제1원칙은 **모든 서술을 실제 코드에 근거시키는 것**이다. 추측·일반론·이상적인 설계가 아니라, 지금 저장소에 있는 코드가 실제로 하는 일을 쓴다.

이 원칙이 중요한 이유: SSOT 문서는 나중에 이 문서만 읽고 판단을 내리는 사람(또는 에이전트)이 신뢰하는 근거가 된다. 코드에 없는 규칙을 지어내거나, 존재하지 않는 이벤트를 상상해서 적으면 문서는 신뢰를 잃고 SSOT로서 무가치해진다. 근거를 댈 수 없는 문장은 쓰지 않는다.

## 핵심 규칙

- **코드 근거 필수**: 규칙·불변식·상태 전이·정책을 서술할 때 반드시 코드 위치(`파일경로:라인` 또는 `파일경로#함수명`)를 함께 적는다. 근거를 못 찾으면 그 문장을 쓰지 않는다.
- **용어 = 코드 식별자**: 문서에서 쓰는 엔티티명·상태명·필드명은 코드의 클래스/enum/변수 이름과 **글자 그대로** 일치시킨다. 번역하거나 의역하지 않는다. (예: 코드가 `RecurringExpense`면 문서도 `RecurringExpense`)
- **본문은 한국어, 식별자는 원문**: 설명 문장은 한국어로 쓰되, 코드 식별자·파일명·도메인 문서 파일명은 영어 원문 그대로 둔다.
- **전체 재생성(덮어쓰기)**: 실행할 때마다 `docs/ssot/`를 현재 코드 기준으로 새로 쓴다. 기존 문서의 수동 편집은 보존하지 않는다 — 항상 코드가 진실의 원천이다. (기존 파일이 있으면 덮어쓴다.)
- **없으면 없다고 쓴다**: 어떤 섹션에 해당하는 코드가 없으면(예: 도메인 이벤트가 구현돼 있지 않음), 억지로 채우지 말고 "구현된 도메인 이벤트 없음" 처럼 명시한다. 빈 섹션을 지어낸 내용으로 채우는 것이 가장 큰 실패다.

## 산출물

위치: `docs/ssot/`

### 공통 문서 (항상)

| 파일 | 내용 |
|------|------|
| `introduction.md` | 프로젝트 개요·목적·핵심 가치, 기술 스택, 모노레포 구성 |
| `architecture.md` | 모듈 구조, 레이어(controller/service/repository 등) 설명, 요청 흐름, 모듈 간 의존 |
| `database.md` | DB 스키마(테이블·컬럼·타입·관계), 인덱스, 마이그레이션 전략 — **DB가 없으면 생성하지 않는다** |
| `serialization.md` | 요청/응답 직렬화 규칙, DTO ↔ 응답 형식 컨벤션, 공통 응답 엔벨로프, 날짜·금액 등 표현 규칙 |
| `tests.md` | 테스트 전략(E2E/통합/단위), 실행 방법, 커버리지 방침, 테스트 구조 컨벤션 |
| `conventions.md` | 코드 컨벤션(네이밍·파일 구성 등), 커밋 메시지 규칙, 브랜치 전략 |

공통 문서 템플릿과 각 문서에 채울 항목은 `references/common-docs.md`를 읽고 따른다.

### 도메인 문서 (도메인마다 1개)

파일명: `{business-domain-english}.md` (비즈니스 개념 기준. 예: `authentication.md`, `ledger.md`, `backup.md`)

각 도메인 문서는 아래 8개 섹션을 모두 포함한다. 상세 템플릿·작성 지침·좋은 예/나쁜 예는 `references/domain-doc.md`를 읽고 따른다.

1. 용어 정의 (코드 식별자와 일치)
2. 핵심 엔티티와 애그리게이트 (애그리게이트 루트 명시)
3. 불변식(invariant)
4. 상태와 상태 전이 규칙
5. 비즈니스 규칙/정책 (코드 위치 명시)
6. 도메인 이벤트 (이름·발생 조건·payload)
7. 컨텍스트 경계와 책임 (다루는/안 다루는 범위, 타 도메인 관계)
8. 예외/에러 케이스 (에러 코드 포함)

## 작업 순서

이 순서를 그대로 따른다. TodoWrite로 각 단계를 추적하면 좋다.

### 1. 코드베이스 인벤토리 (탐색)

문서를 쓰기 전에 코드가 실제로 무엇을 하는지 파악한다. 서브에이전트가 있으면 병렬로 조사해 속도를 높인다. 최소한 아래를 확인한다:

- **진입점·구성**: 앱 엔트리(`main.ts`, `app.module.ts`, Next `app/`), 패키지 구성(모노레포면 워크스페이스), 실행 스크립트.
- **레이어·모듈**: 도메인 모듈 디렉터리, controller/service/repository/DTO 계층, 공통(common) 유틸.
- **DB**: 스키마 파일(예: `prisma/schema.prisma`), 마이그레이션 디렉터리, 엔티티↔테이블 매핑. DB가 없으면 `database.md`는 생략한다.
- **직렬화**: 응답을 감싸는 인터셉터/필터, DTO 클래스, 공통 응답 형식, 예외 필터(에러 응답 형식·에러 코드).
- **테스트**: 테스트 러너 설정, unit/e2e 위치와 네이밍, 실행 커맨드.
- **컨벤션 근거**: `CLAUDE.md`, `.claude/rules/`, ESLint/Prettier 설정, 커밋/브랜치 규칙 문서.

> 추측하지 말고 파일을 실제로 열어 확인한다. 프로젝트에 `CLAUDE.md`나 `docs/PRD.md`가 있으면 배경 이해에 쓰되, **문서에 적는 규칙의 근거는 코드**로 다시 확인한다.

### 2. 비즈니스 도메인 식별

모듈 디렉터리 이름을 그대로 도메인으로 삼지 않는다. **비즈니스 개념** 기준으로 도메인을 구분한다. 라우트·서비스·엔티티가 다루는 "사용자에게 의미 있는 기능 묶음"을 찾아 그룹핑한다.

- 하나의 코드 모듈이 여러 비즈니스 도메인을 담을 수도 있고(예: 한 모듈 안에 서로 다른 개념), 여러 모듈이 한 도메인을 이룰 수도 있다.
- `common`·`prisma`·설정 같은 순수 인프라는 도메인 문서로 만들지 않는다(architecture.md에서 다룬다).
- 도메인 목록과 각 도메인의 파일명(영어)을 먼저 정해 사용자에게 짧게 보고하고, 이견 없으면 문서 생성을 진행한다.

### 3. 공통 문서 생성

`references/common-docs.md`의 템플릿에 따라 6개(또는 DB 없으면 5개) 공통 문서를 쓴다. 각 문서의 사실은 1단계 인벤토리에서 확인한 실제 코드/설정에 근거한다.

### 4. 도메인 문서 생성

`references/domain-doc.md`의 템플릿에 따라 도메인마다 1개씩 쓴다. 8개 섹션 모두 채우되, 근거 없는 섹션은 "해당 없음/미구현"으로 명시한다. 각 규칙·전이·이벤트에 코드 위치를 붙인다.

### 5. 자체 검증

문서를 다 쓴 뒤 아래를 점검한다(체크리스트는 아래 절 참고). 특히 **문서에 등장하는 식별자가 실제 코드에 존재하는지** grep으로 재확인한다 — 지어낸 이름이 섞이면 SSOT가 깨진다.

## 완료 전 체크리스트

- [ ] `docs/ssot/`에 공통 문서(introduction/architecture/serialization/tests/conventions, +DB 있으면 database)가 모두 있다
- [ ] 각 비즈니스 도메인마다 `{domain}.md`가 있고 8개 섹션을 모두 포함한다
- [ ] 모든 용어·엔티티명·상태명이 코드 식별자와 글자 그대로 일치한다 (grep으로 확인)
- [ ] 불변식·정책·상태 전이·이벤트마다 코드 위치(`파일:라인` 또는 `파일#함수`)가 붙어 있다
- [ ] 근거를 못 찾은 항목은 지어내지 않고 "해당 없음/미구현"으로 표기했다
- [ ] 본문은 한국어, 코드 식별자·파일명은 영어 원문이다
- [ ] DB가 없는 프로젝트면 `database.md`를 만들지 않았다

## 안티패턴 (하지 말 것)

- 코드를 안 열고 파일명·CLAUDE.md·주석만 보고 규칙을 추정해서 쓰기 → 반드시 구현으로 확인.
- "일반적으로 ~해야 한다" 같은 교과서적 서술 → 이 코드가 실제로 무엇을 하는지만 쓴다.
- 코드에 없는 도메인 이벤트/상태/에러 코드를 상상해서 채우기 → 없으면 없다고 쓴다.
- 문서 용어를 한국어로 의역해 코드 식별자와 불일치 만들기 → 식별자는 원문 유지.
